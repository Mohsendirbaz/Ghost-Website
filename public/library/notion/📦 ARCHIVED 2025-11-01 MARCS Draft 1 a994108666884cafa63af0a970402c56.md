## 1. Project Vision & Core Challenge

### 1.1 What Are We Building?

We are building a **multi-agent system for collaborative book writing** that can produce high-quality, coherent manuscripts at scale. Specifically, we’re targeting two books simultaneously:

- **Book 1:** “Prosecuting Inequity” (Climate change & economic justice, 28 chapters)
- **Book 2:** “Dishonest AI is Dangerous AI” (AI ethics & governance, 28 chapters)
**Total scope:** 56 chapters with complex interdependencies across both books.
    
    ### 1.2 Why Is This Hard?
    
    Writing a book is not just about generating text. It requires:
    
1. **Narrative coherence** - Chapter 15 must reference events from Chapter 3
2. **Thematic consistency** - The “monopoly power” theme appears in both books
3. **Citation integrity** - All claims must be backed by verifiable sources
4. **Multi-scale unity** - Coherence at:
    - Book level (coarse) - overall argument flow
    - Chapter level (medium) - section-to-section connections
    - Scene level (fine) - paragraph-to-paragraph transitions
5. **Cross-book coordination** - Climate Ch 3 “Decarbonization” must align with AI Ch 1 “AI Monopoly Power”
    
    ### 1.3 The Central Problem
    
    **How do multiple specialized agents (writer, editor, fact-checker, etc.) coordinate their work when:**
    
- They don’t know all dependencies upfront
- They discover new connections during writing
- They need to maintain consistency across 56 chapters
- They can’t hold the entire context in working memory
This is fundamentally a **distributed coordination problem** with incomplete knowledge and emergent complexity.

## 2. Why Traditional Approaches Fail

### 2.1 The Naive Solution: Command & Control

**Idea:** “Let’s have a central controller tell each agent exactly what to do, step by step.”
**Why it fails:**

- **Brittle:** Any unexpected discovery breaks the entire plan
- **Inflexible:** Can’t adapt to new insights during writing
- **Bottleneck:** Central controller becomes overwhelmed with decisions
- **Ignorance:** You can’t plan what you don’t know yet
**Real example:** Writer discovers that Chapter 7’s economic argument actually depends on Chapter 3’s infrastructure discussion. The pre-made plan didn’t account for this, so now what?
    
    ### 2.2 The Distributed Systems Approach
    
    **Idea:** “Let’s use distributed consensus protocols like Raft or Paxos to coordinate agents.”
    **Why it’s overkill:**
    
- **Wrong problem:** We’re not solving Byzantine fault tolerance
- **Unnecessary complexity:** We don’t need replicated state machines
- **Performance penalty:** Consensus protocols add latency to every operation
- **Missing the point:** Our problem isn’t about consistency models (strong vs. eventual) - it’s about managing a **referential graphKey insight:** No amount of computational power or distributed systems theory will solve the *fundamental* problem: **maintaining coherent references across a massive knowledge graph.**
    
    ### 2.3 The Real Challenge
    
    The problem isn’t computing power or consensus - it’s **graph coherence with incomplete knowledge.**
    We have:
    
- 56 nodes (chapters) in a dynamic graph
- Edges are **referential strands** (citations, callbacks, foreshadowing)
- Edges are discovered incrementally during writing
- Agents need to reason about multi-hop paths (Chapter 1 â†’ 7 â†’ 15)
- Coherence must be maintained at three scales simultaneously
**This requires a different approach.**

## 3. The Single Source of Truth Philosophy

### 3.1 The Core Insight

**You fight fire with fire.** If the problem is fragmented, inconsistent knowledge, the solution is:
**One authoritative representation that everyone queries.**
Not a distributed database. Not replicated state. Not eventual consistency.
**A single, hierarchical, query-able structure that represents the complete state of the book project.**

### 3.2 Why Single Source of Truth (SSoT)?

**Mathematical guarantee:** If all agents read from the same source, they cannot have conflicting views of reality (assuming synchronous reads).
**Practical benefit:** Eliminates an entire class of problems:

- âŒ No replication lag
- âŒ No consistency conflicts
- âŒ No Byzantine failures
- âŒ No split-brain scenarios
- âœ… Instant consistency by definition
    
    ### 3.3 The Trade-off
    
    **Give up:** Parallel writes to the same entity (but we don’t need this - chapters are written sequentially)
    **Gain:** Perfect consistency, simpler reasoning, provable correctness
    
    ### 3.4 Implementation Choice: Asana
    
    We chose **Asana** as our single source of truth because:
    
1. **Mature platform** - Production-ready, enterprise-scale infrastructure
2. **Rich hierarchy** - Portfolio â†’ Goal â†’ Project â†’ Task â†’ Subtask (perfect for books)
3. **Custom fields** - Heterogeneous metadata across entity types
4. **Reference fields** - Native support for entity-to-entity links
5. **REST API** - Programmatic access for agents
6. **No maintenance** - We don’t build/maintain the infrastructure
**Asana becomes our hierarchical database.** Not a task tracker - a **graph database with a hierarchical schema.**

## 5. Referential Strands: The Connective Tissue

### 5.1 What Is a Referential Strand?

A **referential strand** is a typed connection between two entities in our Asana graph.
**Example:**

```
Chapter_2 --[Foreshadowing]--> Chapter_8
Chapter_8 --[Callback]-------> Chapter_2
```

This creates a **bidirectional semantic link:** Chapter 2 sets up something that Chapter 8 pays off.

### 5.2 Types of Referential Strands

We use custom fields to encode different relationship types:
| Field Name | Type | Purpose | Example |
|————|——|———|———|
| `Chapter_References` | Reference[] | General cross-references | Ch7 cites argument from Ch3 |
| `Foreshadowing_Targets` | Reference[] | Setup for later | Ch2 hints at Ch8’s revelation |
| `Callbacks_From` | Reference[] | Pays off earlier setup | Ch8 resolves Ch2’s question |
| `Plot_Thread_IDs` | Multi-select | Narrative continuity | All chapters with “PROPHECY” thread |
| `Shared_Themes` | Multi-select | Thematic connections | “MONOPOLY_POWER” spans both books |
| `Character_Appearances` | Multi-select | Character arcs | Track protagonist’s journey |

### 5.3 Unlimited Strands, Intentional Entanglement

**Key insight:** We don’t limit the number of references. A chapter can reference 20 others if needed.
**Why?** Because this creates **useful entanglement** - the dense network of references is what makes the book coherent.
**Graph density as quality metric:**

```
Coherence â‰ˆ Average_References_Per_Chapter
Low coherence (bad): 2-3 refs/chapter (isolated chapters)
Medium coherence: 5-8 refs/chapter (some connections)
High coherence (good): 10-15 refs/chapter (tightly woven narrative)
```

### 5.4 Discovery During Writing

**Critical property:** Strands are discovered incrementally.
**Process:**

1. Writer drafts Chapter 7
2. Realizes it depends on infrastructure argument from Chapter 3
3. **Adds reference:** `Chapter_7.Chapter_References += [Ch_3_GID]`
4. System now knows this dependency
5. Editor can see all references when editing Chapter 7
6. QA agent can verify the reference is valid
**This is why pre-planning fails:** You can’t know all references upfront. They emerge during the creative process.

## 6. Multi-Scale Coherence

### 6.1 The Three Scales

Book coherence isn’t uniform - it exists at three granularities:
**Scale 1: Book Level (Coarse)**

- Relationships between entire books or major parts
- Example: “Book 1’s climate economics framework supports Book 2’s AI governance argument”
- Granularity: ~10-20K words per node
**Scale 2: Chapter Level (Medium)**
- Relationships between chapters within and across books
- Example: “Chapter 3’s infrastructure analysis connects to Chapter 7’s labor discussion”
- Granularity: ~2-5K words per node
**Scale 3: Scene Level (Fine)**
- Relationships between scenes and paragraphs
- Example: “Scene 2.3’s economic data backs up Scene 5.1’s policy argument”
- Granularity: ~500-1000 words per node
    
    ### 6.2 Coherence Function
    
    We measure coherence between two entities using:
    
    ```python
    def coherence(entity_a, entity_b):
    """Calculate coherence score between two entities.
    ```
    

Returns: float in [0, 1]
““”

refs_a = set(entity_a.custom_fields[“Chapter_References”])
refs_b = set(entity_b.custom_fields[“Chapter_References”])

# Shared references (intersection)

shared = refs_a & refs_b

# Total references (union)

total = refs_a | refs_b

if not total:
return 0.0

# Jaccard similarity

jaccard = len(shared) / len(total)

# Depth weighting (more shared refs = deeper connection)

# Combined score

```

## 9. Sorting & Reordering Algorithms

### 9.1 Why We Need Sorting

**Challenge:** 56 chapters with complex dependencies. What order should agents work on them?
**Naive approach:** Sequential (Ch 1 â†’ Ch 2 â†’ … â†’ Ch 56)
**Problem:** This ignores:

- Parallel work opportunities (Ch 10 doesn’t depend on Ch 9)
- Priority levels (critical chapters first)
- Coherence optimization (highly-connected chapters near each other)
**Solution:** Sophisticated sorting algorithms on discretizable domains.
    
    ### 9.2 Five Sorting Algorithms
    
    **Algorithm 1: Topological Sort**

    """Order chapters respecting dependency DAG.
    ```

 """Find all chapters this depends on (direct + indirect)."""
 visited = set()
 queue = collections.deque([(chapter, 0)])

while queue:
 current, depth = queue.popleft()

visited.add(current.gid)
